0既存プロジェクトを使う場合

すでに yamatype16 プロジェクトを作成済みの場合。

  • 作り直す必要はありません。そのまま使えます
  • MVPのSQLには冒頭に旧テーブルの削除文が入っているので、上書き実行できます
  • セクション2・3を飛ばして、セクション4（SQL実行）から始めてください
  • APIキーの取得（セクション5）も済んでいれば飛ばせます
新しいプロジェクトを作りたい場合のみ、セクション2から読んでください。プロジェクトを分けるとGoogle OAuthの設定をやり直す必要があるので、特に理由がなければ既存を使う方が早いです。

1準備するもの

  • GitHubアカウント（Supabaseへのサインインに使うのが手軽）
  • Googleアカウント（Google Cloudの設定に使用）
  • MVP DB設計書のSQL全文（hikers-card-db-mvp-v1.html のセクション6）
  • 開発用のローカルサーバー。npx serve などで http://localhost:3000 で開ける状態にしておくと後の設定が楽
費用：無料プランで始められます。ただし7日間アクセスがないとプロジェクトが一時停止します（管理画面から復帰可能、データは消えません）。開発中に間が空きそうなら、週に一度でも開いておくと安心です。

2組織（Organization）を作る

Supabaseでは、プロジェクトの前に組織を作ります。プロジェクトをまとめる入れ物で、ユーザーには一切見えません。

  1. https://supabase.com でサインアップ（GitHub連携が早い）
  2. Create a new organization の画面が出る
  3. 入力は下記のとおり
Create a new organization
Name自動入力のままでOK
（後から変更可）
TypePersonal
PlanFree - $0/month
組織名はユーザーに見えないので、こだわる必要はありません。

3プロジェクトを作る

  1. New project を選ぶ
  2. 下記のとおり入力する
  3. Create new project を押して、構築完了まで2分ほど待つ
New project
GitHub (optional)空のままでOK
Project namehikers-card など
分かる名前に変更
Database passwordCopyして必ず保存
RegionNortheast Asia (Tokyo)
Database password は、この画面を離れると二度と確認できません。Copyボタンを押して、パスワード管理ツールやメモに必ず保存してください。SQL Editorを使う分には不要ですが、外部ツールから繋ぐときに必要になります。
Region は「Asia-Pacific」ではなく「Northeast Asia (Tokyo)」を選ぶ。ドロップダウンを開くと地域グループの下に個別のリージョンが並びます。日本のユーザー向けなので、東京にすると応答速度が変わります。

Security 設定（3つ）

同じ画面の下部にあります。ここは判断が要るので個別に説明します。

項目設定と理由
Enable
Data API		オン。supabase-jsから接続するのに必要です
Automatically
expose new tables		オン。Supabaseは無効化を推奨していますが、それは手動で権限管理する前提の話です。設計書のSQLには権限付与（GRANT）を書いていないので、オフにするとRLSが正しくてもアクセスできずエラーになります。RLSで守る設計なので、オンのままで問題ありません
Enable
automatic RLS		オン推奨。新しくテーブルを作ったとき自動でRLSが有効になる安全装置です。設計書のSQLでも全テーブルにRLSを設定しているので重複しますが、二重に有効化しても害はありません。将来の設定漏れを防げます

4テーブルを作る（SQL実行）

  1. 左メニューの SQL Editor を開く
  2. New query を選ぶ
  3. MVP DB設計書のセクション6「SQL全文」をすべてコピーして貼り付ける
  4. Run（またはCtrl/Cmd + Enter）で実行
必ず一度にまとめて実行してください。SQLは上から順に依存関係があるので、分割して実行するとエラーになります。
冒頭に旧テーブルの削除文が入っているので、すでにテーブルがあっても そのまま実行できます（前回のような「already exists」エラーは起きません）。

できたか確認する

Table Editorで7テーブルが見えるはずです。あわせてSQLでも確認します。

-- RLSが全テーブルで有効か（7行すべて true になるはず）
select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
order by tablename;

-- 関数ができているか（8つ並ぶはず）
select routine_name
from information_schema.routines
where routine_schema = 'public'
order by routine_name;
できるテーブル（7つ）：blocks / climbed_mountains / exchanges / exchange_tokens / mountains / profiles / reports
できる関数（8つ）：get_my_collection / get_public_card / handle_new_user / issue_exchange_token / on_block_created / protect_profile_fields / random_public_id / random_token / redeem_exchange_token
山マスタ（mountains）は空のままです。百名山100座のデータは別途投入します。空でもアカウント作成と交換の動作確認はできます。

5APIキーを取得する

Supabaseはキーの形式を移行中で、従来のanonキーは2026年末に廃止予定です。新形式を使います。

  1. Project Settings → API Keys を開く
  2. publishable key（sb_publishable_...）をコピーして控える
  3. Project Settings → Data API でプロジェクトURL（https://xxxxx.supabase.co）も控える
キー扱い
publishable
公開OK		フロントのJavaScriptに直接書いてよい。RLSが効くので、これだけでは他人のデータを読めない
secret
絶対に出さない		RLSをすべて無視できるキー。GitHubにも、フロントのコードにも、絶対に書かない。今回の実装では登場しません
secretキーを誤って公開すると、全ユーザーのデータが読み書きされ放題になります。「publishableキーだけをコードに書く」と覚えてください。

6Google OAuthを設定する

ここが一番手数の多い工程です。Google側とSupabase側を行き来するので、両方のタブを開いておくと楽になります。

6-1. SupabaseのコールバックURLを控える

  1. Authentication → Sign In / Up → Auth Providers を開く
  2. Google を選んで展開する
  3. Callback URL (for OAuth) をコピーする。https://xxxxx.supabase.co/auth/v1/callback の形

6-2. Google Cloud側の設定

Google Cloudの認証まわりは「Google Auth Platform」という画面に集約されています（以前の「OAuth同意画面」から変更されました）。

  1. https://console.cloud.google.com でプロジェクトを新規作成（名前は何でも可）
  2. Google Auth Platform を開く（console.cloud.google.com/auth/overview）
  3. Audience：ユーザーの種類を External にする。個人開発なのでこちら
  4. 同じAudienceの画面で、自分のGoogleアカウントをテストユーザーとして追加する。これを忘れると自分でもログインできません
  5. Data Access（スコープ）：userinfo.email と userinfo.profile は既定で入っています。openid だけ手動で追加してください
  6. Clients → Create client → 種類は ウェブ アプリケーション
  7. 承認済みの JavaScript 生成元：サイトのURL（開発中なら http://localhost:3000）を追加
  8. 承認済みのリダイレクト URI：6-1で控えたSupabaseのコールバックURLを貼る
  9. 作成すると クライアントID と クライアントシークレット が表示されるのでコピー
スコープは増やさないこと。必要以上のスコープ（Gmail読み取りなど）を追加すると、Googleの審査対象になって公開までに何週間もかかります。上記3つだけなら審査は不要です。

6-3. Supabaseに貼り戻す

  1. Supabaseの Auth Providers → Google に戻る
  2. Enable Sign in with Google をオンにする
  3. クライアントIDとクライアントシークレットを貼り付けて Save

6-4. リダイレクトURLを許可リストに登録

認証後にユーザーが戻ってくる先を、Supabaseに事前登録します。ここを忘れると認証後に画面が戻らず、原因も分かりにくいので必ず設定してください。

  1. Authentication → URL Configuration を開く
  2. Site URL：本番URL（未定なら http://localhost:3000）
  3. Redirect URLs に、開発用と本番用の両方を追加しておく
    例：http://localhost:3000/** と https://本番ドメイン/**
末尾に /** を付けておくと、パスの違いで弾かれなくなります。

7メール認証（マジックリンク）を設定する

  1. Authentication → Sign In / Up で Email が有効になっていることを確認（既定でオン）
  2. Confirm email をオンにする
  3. Authentication → Emails でメール本文を日本語にする
開発中のメール送信数には上限があります（1時間あたり数通程度）。テストを繰り返すとすぐ頭打ちになるので、普段のテストはGoogleログインで行い、マジックリンクは動作確認のときだけ使うのが現実的です。
公開時には独自のメール配信サービス（Resend、SendGridなど）をSMTPとして設定する必要があります。これは公開直前でよく、今は不要です。

8動作確認

フロントを1行も書かないうちに、SQL Editorだけで交換の仕組みまで確認できます。ここで動けば、あとは画面を作るだけです。

確認1：アカウント作成でprofiles行が自動生成されるか

  1. Authentication → Users → Add user でテスト用アカウントを2つ作る（交換のテストに2人必要）
  2. Table Editor → profiles を開く
  3. 行が2つ自動で増えていれば成功。public_idにランダムな6文字、card_noに連番が入っているはず
これが動いていれば、トリガー（handle_new_user）とID自動生成が正しく動作しています。

確認2：カードが公開できるか

-- profilesから2人のidとpublic_idを確認しておく
select id, public_id, card_no from public.profiles;

-- 1人目に表示名と診断結果を入れる（idは上で確認したものに置き換え）
update public.profiles
   set display_name = 'テスト太郎', comment = 'よろしくお願いします',
       type_code = 'PGLA', axis_pe = 73, axis_sg = 33, axis_lf = 60, axis_ca = 47
 where public_id = '1人目のpublic_id';

-- 公開カードを取得してみる
select public.get_public_card('1人目のpublic_id');
期待する結果：表示名・カード番号・診断タイプ・4軸を含むJSONが返る。
表示名を空に戻して再実行すると null が返るはずです。これが「表示名が未設定なら公開しない」という設計どおりの挙動です。

確認3：交換の仕組みが動くか ここが本番

SQL Editorは管理者権限で動くので auth.uid() が空になります。ユーザーになりきるために set local role と request.jwt.claims を使います。

-- 2人目にも表示名を入れておく
update public.profiles set display_name = 'テスト花子'
 where public_id = '2人目のpublic_id';

-- ① 1人目になりきってトークンを発行
begin;
  select set_config('request.jwt.claims',
    json_build_object('sub', '1人目のid')::text, true);
  set local role authenticated;
  select public.issue_exchange_token();
commit;

-- ② 2人目になりきって、そのトークンで交換
begin;
  select set_config('request.jwt.claims',
    json_build_object('sub', '2人目のid')::text, true);
  set local role authenticated;
  select public.redeem_exchange_token('①で出たトークン');
commit;

-- ③ 交換記録ができているか
select * from public.exchanges;

-- ④ 2人目のコレクションに1人目がいるか
begin;
  select set_config('request.jwt.claims',
    json_build_object('sub', '2人目のid')::text, true);
  set local role authenticated;
  select public.get_my_collection();
commit;
期待する結果：②で {"ok": true, "is_new": true, ...} が返り、③で1行できて、④に相手のカードが入っている。
同じトークンでもう一度②を実行すると、is_new が false になり、exchangesは1行のままのはずです（再交換の上書き挙動）。

確認4：不正な交換が弾かれるか

-- 自分自身のトークンは使えない
begin;
  select set_config('request.jwt.claims',
    json_build_object('sub', '1人目のid')::text, true);
  set local role authenticated;
  select public.redeem_exchange_token('1人目が発行したトークン');
commit;
-- → {"ok": false, "reason": "self"} が返る

-- 期限切れのトークンは使えない（手動で期限を過去にして試す）
update public.exchange_tokens set expires_at = now() - interval '1 minute';
-- → もう一度 redeem すると {"ok": false, "reason": "expired"}

-- ブロックすると交換記録が自動削除される
insert into public.blocks (blocker_id, blocked_id)
values ('1人目のid', '2人目のid');
select * from public.exchanges;
-- → 0行になっているはず
ここまで確認できれば、設計が意図どおりに機能しています。フロントにバグがあっても、DBが最後の砦として不正な交換を防ぎます。
