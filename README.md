# ハイカーズカード｜フロントエンド Step 17（山の登録の統合・カードの整理）

Phase 1 の全機能 ＋ PWA化 ＋ **デザイン強化**。

Step 8 で追加したもの：
- カードの**背景デザイン5種類**（マイページから選択）
- **共通ヘッダー**（下スクロールで隠れ、上で現れる／ドロワーメニュー）
- 登った山の**折りたたみ**（踏破数を押すと開く）
- **好きな山・登ってみたい山**（各5座まで）
- **SNSリンク**（YAMAP / ヤマレコ / Instagram / X）

## 診断について

- `data.js` と `characters.js` は**筑波山版からそのままコピー**したもの。計算ロジックも `calcResult` と同一
- 結果は `type_code` と4軸スコア（1文字目側への寄り0〜100）としてDBに保存される
- **未ログインでも診断を受けられる。** その場合は結果をブラウザに一時保存し、ログイン完了後に自動で書き込む
- **やり直しは制限なし**
- シークレットキャラは MVP では移植していない（`type_code` が4文字英大文字に限定されているため）

## 手順

### 1. config.js を書き換える

```js
export const SUPABASE_URL = "https://xxxxxxxxxxxx.supabase.co";
export const SUPABASE_PUBLISHABLE_KEY = "sb_publishable_xxxxxxxxxxxxxxxx";
```

- **URL**：Supabase → Project Settings → Data API
- **publishable key**：Supabase → Project Settings → API Keys

`sb_secret_` で始まるキーは**絶対にここに書かないでください**。

### 2. ローカルサーバーを起動する

**ファイルをダブルクリックして開いてはいけません。** `file://` では動きません（モジュールの読み込みが許可されないため）。

ポートは **3000** にしてください。SupabaseのRedirect URLsに `http://localhost:3000/**` を登録してあるためです。

```bash
cd hikers-card
npx serve -l 3000
```

Pythonでも構いません。

```bash
python3 -m http.server 3000
```

### 3. ブラウザで開く

```
http://localhost:3000
```

**登ってよかった山が保存されなかった原因：** `climbed_mountains` に UPDATE のポリシーが無く、RLSが更新を黙って拒否していました。RLSが有効なテーブルでは、ポリシーの無い操作は**エラーも出さずに0行更新で終わります**。気づきにくいので、画面側でも更新件数を確認するようにしました。

**同じ見落としを防ぐために：** 定期的に次のSQLで、各テーブルのポリシーに漏れがないか確かめてください。

```sql
select tablename, string_agg(distinct cmd, ', ' order by cmd) as policies
  from pg_policies where schemaname = 'public'
 group by tablename order by tablename;
```

**`upsert` を使うテーブルには insert と update の両方が要ります。**upsert は行がすでにあるとUPDATEとして動くためです。

- 「宝剣岳」「西穂独標」を岩稜・難所から山頂へ。踏破状況では「その他の山」に数えられる。登録はそのまま

`hikers-card-step27.sql` にも同じ変更を入れてあるので、Step 27 を実行し直しても元に戻らない（山頂は「所属する山」を持たず、エリアだけを所属の山から決める）。

### カニのタテバイ・ヨコバイの削除（Step 30）

`hikers-card-step30.sql` を SQL Editor で実行する（フロントの変更はなし）。剱岳があれば十分なので、岩稜・難所から外した。すでに登録している人のデータは剱岳に引き継ぐ（登った山・登ってみたい山は剱岳に置き換え、登ってよかった山は剱岳がまだ選ばれていなければ順位を引き継いで1位から詰め直す）。`hikers-card-step27.sql` からも外してあるので、Step 27 を実行し直しても復活しない。

**登山相性の計算（`affinity.js`）：**4軸の近さ（目的・仲間は差がそのまま効く、計画・リスクは違っても補いあえるので差の影響を半分）を0.8、山の重なり（登ってみたい山が同じ×3、よかった山が同じ×2、片方の登ってみたい山にもう片方が登った×1、6点で満点）を0.2で足し、`50 + 50 × raw^1.5` で 50〜100 にしています。ランダムな組み合わせ5,000組で試すと中央値76・下位10%で68・上位10%で84、正反対のタイプどうしで53前後、同じタイプで共通の山も多いと100になります。重みや式は `affinity.js` の冒頭にまとめてあります。


**デザインの方針（Step 17 で刷新）：**丸ゴシックと色数の多さが子供っぽく見える原因だったため、角ゴシック（Noto Sans JP）＋欧文 Inter にし、各テーマの色を「文字色1色＋アクセント1色」に絞りました。装飾（足跡・メダル・塗りつぶしのタグ）は減らし、余白と文字の太さの差で見せています。模様はLinktreeのパネルのようにヒーローカードの中だけにはっきり敷き（`patternSVG`）、ページはカードと同系色の少し深い無地にしてカードを引き立てています。PCでは幅を約580pxまで広げています（`.wrap` の `max-width`）。

**画像の作り方について：**`card-image.html` で公開ページと同じデータ（`get_public_card`）からカードを描き、[html2canvas](https://html2canvas.hertzen.com/) で PNG にしています。html2canvas は SVG を単独の画像として描くため CSS の色が効かなくなるので、描く直前に計算済みの色を SVG の属性へ書き写しています。また内側の影（`box-shadow: inset`）を塗りつぶしの四角として描いてしまうため、画像用のカードでは外側の影だけにしています。

**登ってよかった山の順位について：**Step 17 の SQL を流した時点で登録済みだった「よかった山」には、これまでの表示順（標高の高い順）で1位から仮の順位が振られます。

**保存を1回にまとめた理由：**3つのタブを行き来しながら選ぶため、別々に保存すると「登った山だけ保存されて、よかった山は失敗した」という半端な状態が起き得ます。`save_my_mountains` は1つの関数（1トランザクション）で全部を書き換えるので、途中で失敗しても何も変わりません。上限（各5座）や「よかった山は登った山から」のチェックもDB側で行っています。

**アイコンの変更について：**Service Worker の `VERSION` を `v2` に上げたので、古いアイコンのキャッシュは自動で捨てられます。ただしiPhoneのホーム画面に追加済みのアイコンは、一度削除して追加し直さないと古いままのことがあります。

### Service Worker の方針

**Step 17 から、ページ・スクリプト・CSSは毎回サーバーに「新しくなっていないか」を確かめるようにしました**（`sw.js` の `cache: "no-cache"` と、`vercel.json` の `Cache-Control: no-cache`）。変わっていなければ中身は送られないので、通信量はほとんど増えません。

**キャッシュはほとんど使っていません。**

開発中に頻繁に更新するサイトでキャッシュを効かせすぎると、「直したのに反映されない」という厄介な問題が起きます。ユーザー側でキャッシュを消してもらうのは現実的ではありません。

またこのサービスは、交換もコレクションもサーバーのデータが必要なので、**オフラインで使える場面がほとんどありません**。

そのため、キャッシュするのはアイコンなど**めったに変わらないものだけ**にしてあります。ページやスクリプトは常にネットワークから取りに行きます。

将来キャッシュを増やす場合は、`sw.js` の `VERSION` を上げると古いキャッシュが自動で捨てられます。

## カメラについて

- ブラウザでカメラを使うには**HTTPSが必須**。Vercel（HTTPS）か `localhost` でのみ動く
- スマホの実機からローカルサーバーに繋いでのテストは動かない
- 初回に「カメラへのアクセスを許可しますか」と出る。断られた場合は、コードの手入力に誘導している
- 画面を離れるときは必ずカメラを停止している（つけっぱなしを防ぐ）

## ルーティングについて

`vercel.json` の rewrites で2つのパスを繋いでいます。**このファイルをリポジトリの直下に置くのを忘れないでください。**

| パス | 中身 | 用途 |
|---|---|---|
| `/u/:id` | `u.html` | 公開カードページ |
| `/x/:token` | `x.html` | QRから開く交換ページ |

`u.html` と `x.html` では、CSSやJSの参照を**絶対パス**（`/style.css` など）にしています。`/u/x7k2p9` のような階層のあるパスで表示されるため、相対パスだと `/u/style.css` を探してしまうからです。

## つまずきやすいところ

| 症状 | 原因と対処 |
|---|---|
| 画面が真っ白 | ブラウザの開発者ツール（F12）でコンソールを確認。config.js の値が未設定だとここで止まる |
| `file://` で開いて動かない | ローカルサーバーを立ててください（手順2） |
| Googleログイン後に戻ってこない | Supabase → Authentication → URL Configuration の Redirect URLs に `http://localhost:3000/**` があるか確認 |
| Googleが「アクセスをブロック」 | Google Auth Platform → 対象（Audience）のテストユーザーに自分のアカウントを追加 |
| 「プロフィールを読み込めませんでした」 | profiles にトリガーで行が作られていない。SQL Editor で `select * from public.profiles;` を確認 |
| マジックリンクが届かない | 送信数の上限（1時間に数通）に達している可能性。普段はGoogleログインでテストする |
| ポートが 3000 以外 | Redirect URLs に登録したポートと一致させるか、Supabase側に追加する |
| デプロイしたのに一部だけ古い（CSSは新しいのにJSが古い など） | まず `https://（サイト）/card.js` を直接開き、新しいコードが入っているか確かめる。入っていなければリポジトリの差し替え漏れ。入っていればキャッシュなので、アプリ（ホーム画面から開いたもの）を完全に終了して開き直す。Step 17 以降は `vercel.json` と `sw.js` で毎回サーバーに確かめる設定にしてある |

## 補足

- `detectSessionInUrl` を有効にしてあるので、Googleから戻ってきたときもマジックリンクを踏んだときも、Supabaseのライブラリが自動でセッションを作ります。コールバック用のページを自分で用意する必要はありません
- ページを開いた直後はセッションの復元中なので、**判定が終わるまで「読み込んでいます」を表示**しています。これを省くと一瞬ログアウト状態に見えます
